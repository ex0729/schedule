# SECURITY AND PRIVACY

- 최종 갱신: 2026-08-05
- 이 문서는 설계 기준이며 법률 적합성을 보장하지 않는다.

## 데이터 분류

- 고위험: 개인 일정 제목·장소·메모, 연락처, 기관 담당자 연락처, Auth 토큰.
- 제한: 강사 가능 상태, 회사 연결, 요청 응답, 배정, 활동 지역.
- 내부: 감사 로그, 오류 request ID, 운영 메트릭.
- 공개 가능: 사용자가 승인한 프로필 일부. 기본 공개는 없다.

## 접근 제어

- 인증은 Supabase Auth 쿠키 세션, 서버는 `getUser()`로 검증한다.
- 인가는 사용자 역할 + 활성 회사 멤버십 + 활성 강사 연결 + 리소스 소유권으로 판단한다.
- RLS를 모든 업무 테이블에 켜고 service-role 키는 브라우저 번들에 절대 넣지 않는다.
- 관리자도 목적·범위·감사 없는 전역 접근을 갖지 않는다. break-glass는 후속 설계한다.

## 일정 공개 정책

- 기본은 `availability_only`; 회사 API는 원본 ScheduleEvent를 직렬화하지 않는다.
- 회사별 수준과 유효기간을 적용한 DB 함수/서버 도메인 서비스가 상태만 계산한다.
- `details`라도 개인 일정 상세 공개의 정확한 범위는 `[확인 필요]`이며 명시 동의 UX가 필요하다.
- 연결 해제/기간 만료 시 즉시 접근을 거부하고 캐시도 테넌트 키로 무효화한다.

## 인증·세션·입력

- 이메일 확인, 안전한 비밀번호 정책, rate limit, 유출 비밀번호/봇 방어는 운영 전 구성한다.
- 쿠키는 Secure/HttpOnly/SameSite 정책을 환경에 맞게 검증하고 callback allowlist를 제한한다.
- 클라이언트와 서버에서 입력을 검증하며 서버 결과만 신뢰한다.
- 오류에 계정 존재, 타사 회사, 개인 일정 원문, SQL 원인을 노출하지 않는다.

## 감사·보관·삭제·백업

- 권한 변경, 일정 공개, 민감 조회, 요청/응답/배정 변경은 actor·회사·대상·시각을 append-only 기록한다.
- 감사 로그에는 토큰, 비밀번호, 일정 원문 전체를 저장하지 않는다.
- `[법률 검토 필요]` 계정/일정/감사 로그 보관기간, 파기 방식, 이용자 열람·정정·삭제 절차.
- `[법률 검토 필요]` Supabase 리전과 국외 이전/처리위탁 고지 및 계약.
- 암호화 백업, 접근 분리, 복구 목표(RPO/RTO)와 정기 복구 훈련이 운영 전 필요하다.

## 위협 모델 요약

- IDOR/테넌트 누출: RLS + 서버 인가 + 교차 회사 테스트.
- 사용자 metadata 역할 변조: 권한은 DB 프로필/멤버십에서만 조회.
- 중복 요청/동시 배정: idempotency unique + transaction + version.
- 민감 데이터 로그/캐시 노출: 필드 allowlist, 로그 redaction, private/no-store 정책.
- 세션 탈취/CSRF: 안전한 cookie, origin 검증, framework server action 보호 검증, 민감 작업 재인증 검토.
- 대량 가능성 조회: 회사 연결 범위, 기간/검색 rate limit, 감사 이벤트.
