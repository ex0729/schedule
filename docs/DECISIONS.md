# DECISIONS

결정은 삭제하지 않고 상태를 유지한다.

## ADR-001: 관리형 PostgreSQL/Supabase 우선안

- 날짜/상태: 2026-08-05 / Accepted
- 배경: 빈 저장소에서 다중 조직, RLS, 인증, 실시간 확장을 빠르게 안전한 기본값으로 구성해야 한다.
- 선택지: Supabase / 독립 Next.js+PostgreSQL Auth / 별도 TypeScript 백엔드.
- 결정: Supabase PostgreSQL/Auth + Next.js 서버 계층을 채택한다.
- 이유: 표준 PostgreSQL, RLS, 관리형 Auth/백업 경로와 작은 초기 운영 부담.
- 장점: MVP 속도, DB 수준 격리, 모바일 확장 API. 단점: Auth/RLS 학습, 리전·공급자 종속 검토, SSR SDK 변경 가능성.
- 후속 영향: Supabase 어댑터를 격리하고 마이그레이션을 저장소에서 관리한다.
- 변경 조건: 국내 데이터 상주/계약 요구, 규모·비용, 복잡한 비동기 처리로 독립 백엔드가 유리해질 때.

## ADR-002: 첫 수직 단위는 인증과 단일 역할 선택

- 날짜/상태: 2026-08-05 / Accepted
- 배경: 기존 구현이 없고 후속 모든 리소스가 사용자 신원·역할에 의존한다.
- 선택지: UI 프로토타입 / 인증+역할 / 일정 CRUD 우선.
- 결정: 이메일 가입·확인 callback·로그인·역할 기록·보호 대시보드·로그아웃까지 구현한다.
- 이유: 실제 서버 경계를 먼저 세워 가짜 사용자/클라이언트 권한 구현의 확산을 막는다.
- 장점: 후속 멤버십/RLS 기반. 단점: 외부 Supabase 프로젝트 없이는 E2E 인증을 실행할 수 없다.
- 후속 영향: 다음은 회사·강사 연결과 회사 범위 권한이다.
- 변경 조건: 인증 제공자 또는 동시 역할 정책 승인 시 대체 ADR을 추가한다.

## ADR-003: 역할은 DB 프로필의 불변 값으로 권한 판단

- 날짜/상태: 2026-08-05 / Accepted
- 배경: Supabase user metadata는 사용자가 변경할 수 있어 인가 근거로 부적합하다.
- 선택지: metadata / app_metadata / `user_profiles`.
- 결정: 가입 trigger가 `user_profiles.role`을 1회 기록하고 사용자의 update policy를 두지 않는다.
- 이유: RLS와 서버 양쪽에서 조회 가능한 일관된 권한 근거다.
- 장점: 변조 방지·감사 용이. 단점: 역할 변경은 관리 절차 필요.
- 후속 영향: 동시 역할 승인 시 단일 enum을 멤버십/역할 연결 모델로 대체한다.
- 변경 조건: `[확인 필요]` 동시 역할/역할 전환 정책 확정.

## ADR-004: 일정 구간은 반열린 구간

- 날짜/상태: 2026-08-05 / Proposed
- 배경: 연속 수업의 종료와 시작이 같은 경우를 충돌로 오판하면 안 된다.
- 결정: `[start,end)`와 `start < other.end AND other.start < end`를 사용한다.
- 장점: 경계가 명확하고 PostgreSQL range와 정합. 단점: 이동시간은 별도 규칙 필요.
- 변경 조건: 준비/이동 버퍼 정책 승인.
